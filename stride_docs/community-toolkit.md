# Stride.CommunityToolkit in this repo

**What this doc answers:** "is that method core Stride or the CommunityToolkit?"

Everything below was verified by decompiling the installed assemblies
(`ilspycmd -t <Type> <dll>`) and cross-checking `Client/Program.cs`. Where a claim comes
from a decompiled body, the defining **type + assembly** is cited inline.

---

## 1. Versions and packages

> **The toolkit is `1.0.0-preview.62`. It is versioned independently of Stride `4.3.0.2507`.**
> Do not assume a toolkit package exists at Stride's version number, and do not assume
> toolkit APIs are stable — this is a preview line.

`DemiurgeSharp.csproj` references exactly two toolkit packages:

```xml
<PackageReference Include="Stride.CommunityToolkit.Bepu" Version="1.0.0-preview.62" />
<PackageReference Include="Stride.CommunityToolkit.Linux" Version="1.0.0-preview.62" />
```

Resolved graph (from the `.nuspec` files in `~/.nuget/packages/stride.communitytoolkit*/1.0.0-preview.62/`):

| Package | Pulls in | Purpose |
|---|---|---|
| `Stride.CommunityToolkit` | Stride.Engine / .Particles / .Physics / .UI, all `4.3.0.2507` | the actual helper library — `Stride.CommunityToolkit.dll` |
| `Stride.CommunityToolkit.Bepu` | base toolkit + `Stride.BepuPhysics` + `Stride.BepuPhysics.Debug` | Bepu-flavoured overloads: ground, physics primitives, raycast |
| `Stride.CommunityToolkit.Linux` | base toolkit + `Stride.Core.Assets.CompilerApp` | **build plumbing only** |

All three share toolkit git commit `e55282629a91ee8c1eded57dcf9f5f1ddd72df10`.

### `.Linux` is an empty carrier

`Stride.CommunityToolkit.Linux.dll` contains **no public types**. `ilspycmd -l class` returns only
`<Module>`, `UpdateEngineAutoGenerated` and a serializer factory; its `.xml` doc has an empty
`<members/>`. There is nothing in it to call. It exists solely to drag
`Stride.Core.Assets.CompilerApp` into the restore graph so a code-only project can compile assets.

### `.Windows` is the split sibling — not in play here

`Stride.CommunityToolkit.Windows` is present in the local nuget cache but **not referenced**.
Unlike `.Linux` it does ship API: `Stride.CommunityToolkit.Windows.WindowsDpiManager`
(`EnablePerMonitorV2`, `TryGetDpi`, `GetWindowDpi`) and `GraphicsDeviceContext`. These are Win32
P/Invoke wrappers — unavailable on this platform. If a sample or doc references them, that sample
is Windows-only.

Note the base package also ships `stride/Stride.CommunityToolkit.sdpkg`, which declares an asset
folder `Rendering/DebugShapes/Effects`. In `preview.62` the nupkg ships no files at that path.

## 2. Bootstrapping: `new Game()` + `game.Run(start:, update:)`

Defined by **`Stride.CommunityToolkit.Engine.GameExtensions`** (Stride.CommunityToolkit). Two
overloads, distinguished only by delegate shape — `Action<Scene>`/`Action<Scene, GameTime>` and
`Action<Game>`/`Action<Game>`. In practice named arguments are required to disambiguate, which is
why the repo writes `game.Run(start: Start, update: Update)`.

Decompiled body, condensed:

```csharp
game.Script.Scheduler.Add(RootScript);      // scheduled BEFORE the loop starts
GameBase.Run(context);                       // blocks until exit

async Task RootScript() {
    start?.Invoke(game.SceneSystem.SceneInstance.RootScene);
    while (update != null) {
        update(game.SceneSystem.SceneInstance.RootScene, game.UpdateTime);
        await game.Script.NextFrame();
    }
}
```

What this means in practice:

- `Start(Scene rootScene)` runs **once**, inside a micro-thread, after the scene system exists.
  It receives the live root scene — the same object as `game.SceneSystem.SceneInstance.RootScene`.
- `Update(Scene, GameTime)` runs **once per frame** from that same micro-thread, so it ticks
  alongside normal `SyncScript`s, not before or after them as a special case.
- `RootScene` is re-fetched every frame, so a scene swap is picked up automatically.
- `game.Run(...)` **blocks**. Anything after it in `Program.cs` executes at shutdown.

### How this differs from the Game Studio flow

| Game Studio project | This repo (code-only) |
|---|---|
| `.sdscene` loaded by the engine | scene built imperatively in `Start` |
| root logic in a `ScriptComponent` attached in the editor | root logic in `Start`/`Update` delegates |
| `GraphicsCompositor` is an asset | built by `game.AddGraphicsCompositor()` |
| camera placed in the editor, bound to a slot in the compositor asset | `game.Add3DCamera()` creates the entity and binds slot 0 |

Per-entity behaviour is unchanged — the repo still uses ordinary `SyncScript`s
(`ThirdPersonCameraScript`, `NetTransformScript`, …). Only the *root* is different.

Service registration can happen before `Run` (the repo registers `NetworkManager` and
`PlayerRegistry` at `Program.cs:95-96`); scene construction must happen inside `Start`.

## 4. `Add3DCamera` — and whether a second camera works

`Stride.CommunityToolkit.Engine.GameExtensions.Add3DCamera` (Stride.CommunityToolkit), verified body:

- Throws `InvalidOperationException("Cannot add camera: The GraphicsCompositor does not have any
  camera slots defined.")` when `compositor.Cameras.Count == 0` → **`AddGraphicsCompositor()` first**.
- **Mutates `Cameras[0].Name = cameraName`** (default `"Main"`).
- Creates `new Entity(cameraName)` with a single
  `CameraComponent { Projection = Perspective, Slot = Cameras[0].ToSlotId() }`.
- Default position `CameraDefaults.Initial3DPosition` = `(6, 6, 6)`; default rotation
  `Initial3DRotation` = `(45, -30, 0)` **degrees**, applied as `RotationYawPitchRoll(X, Y, Z)`.
- Sets `entity.Scene = RootScene` and returns the entity. **No controller script is attached** —
  the repo adds its own at `Program.cs:238-242`.

### Calling it twice does not work

`AddGraphicsCompositor` → `GraphicsCompositorHelper.CreateDefault` creates **exactly one**
`SceneCameraSlot`. `Add3DCamera` always binds `Cameras[0]`, so a second call produces two enabled
`CameraComponent`s sharing one slot id. `Stride.Engine.Processors.CameraProcessor.AttachCameraToSlot`
(Stride.Engine 4.3.0.2507) then throws:

```
Unable to attach camera [B] to the graphics compositor.
Another camera, [A], is enabled and already attached to this slot.
```

The throw happens at **Draw** time, not at `Add3DCamera` time — so it looks like a rendering crash,
not a setup mistake.

To actually get a second camera, either:

- set `CameraComponent.Enabled = false` on all but one (the processor skips disabled cameras), or
- add a second `SceneCameraSlot` to `compositor.Cameras`, assign `camera.Slot = newSlot.ToSlotId()`
  by hand, and add a `SceneCameraRenderer` for it.

The toolkit has **no helper** for the second option — that is raw Stride API.

## 5. `Create3DPrimitive` and colliders

Which overload you get is decided by the **options type**, not by the usings:

```csharp
// Games.GameExtensions — no physics component at all (Program.cs:126, createCubes)
game.Create3DPrimitive(PrimitiveModelType.Cube, new Primitive3DEntityOptions { Material = material });

// Bepu.GameExtensions — target-typed `new()` binds to Bepu3DPhysicsOptions (Program.cs:200)
game.Create3DPrimitive(PrimitiveModelType.Sphere, new() { IncludeCollider = false });
```

`Bepu3DPhysicsOptions : Primitive3DEntityOptions` adds two members:
`Component`, defaulting to a **dynamic `BodyComponent` with an empty `CompoundCollider`**, and
`IncludeCollider`, defaulting to `true`.

`Stride.CommunityToolkit.Bepu.EntityExtensions.AddBepuPhysics` decompiled:

- Throws `InvalidOperationException("Entity must have a ModelComponent with a valid model to add
  Bepu physics.")` if there is no model.
- **`IncludeCollider = false` still adds `options.Component`** — it only skips the *shape*. You get
  a dynamic, shapeless rigid body, not a plain entity. The repo relies on this at `Program.cs:200`
  and in `Client/View/ObjectViewFactory.cs:23-24` for `ObjectType.Crate`.
- `IncludeCollider = true` maps the primitive type to a shape and appends it to the
  `CompoundCollider` (only if `Component.Collider is CompoundCollider`):

  | `PrimitiveModelType` | Collider |
  |---|---|
  | Capsule | `CapsuleCollider` (default `Radius = 0.35`) |
  | Cube / RectangularPrism | `BoxCollider` |
  | Cylinder | `CylinderCollider` |
  | Sphere | `SphereCollider` |
  | Plane | `BoxCollider` sized `(X, 0, Y)` — zero thickness |
  | Cone / Teapot / Torus / TriangularPrism | toolkit hull colliders in `Bepu.Colliders` |

- `Material`, `RenderGroup`, `EntityName` and `Size` come from
  `PrimitiveEntityOptions` / `Primitive3DEntityOptions`. When `Material` is null no material is
  added at all and Stride falls back to its own default.

### Neither overload sets `entity.Scene`

`Create3DPrimitive` returns a **detached** entity — the caller must parent it. This is the opposite
of its siblings `Add3DGround`, `Add3DCamera`, `AddDirectionalLight` and `AddProfiler`, all of which
assign `entity.Scene = RootScene` themselves. Easy to miss when mixing the two families.

## 7. Gotchas (all verified)

1. **`AddCleanUIStage` re-enables SSR.** `AddGraphicsCompositor` → `CreateDefault` calls
   `postFx.DisableAll()`. `AddCleanUIStage`'s private `AddPostEffects` then *replaces*
   `PostEffects` with `new PostProcessingEffects()`, whose constructor disables only `Outline`
   and `Fog` — `LocalReflections.Enabled` stays `true`
   (`Stride.Rendering.Images.PostProcessingEffects`, Stride.Rendering). That is exactly the crash
   worked around at `Program.cs:139-143`.

2. **Call order is load-bearing:** `AddGraphicsCompositor()` → `AddCleanUIStage()` →
   `AddSceneRenderer(...)`. `AddCleanUIStage` **overwrites `compositor.Game`**, so any scene
   renderer added before it is silently discarded. `Add3DCamera` needs the compositor.
   `AddGroundGizmo` needs `Add3DGround` first — it looks up the name `"Ground"` and no-ops otherwise.

3. **`RenderGroup31` is reserved** by `AddCleanUIStage` for the UI stage; world rendering uses
   "all groups except Group31". Putting a mesh in Group31 routes it into the UI pass.

4. **`Create3DPrimitive` does not add to the scene**; `Add3DGround` / `Add3DCamera` /
   `AddDirectionalLight` / `AddProfiler` do. Live consequence in this repo: the cube built by
   `createCubes` and the `sphere` at `Program.cs:200` are never parented to `rootScene`, so they
   never render.

5. **`AddProfiler` and `Basic3DCameraController` both route through `DebugTextSystem` /
   `FastTextRenderer`**, which this repo documents as crashing on Vulkan. Avoid both; the HUD
   (`TextBlock` via SpriteBatch) is the working alternative.

6. **`AddParticleRenderer` throws a bare `NullReferenceException`** (not a helpful message) if the
   compositor lacks Opaque/Transparent stages. Currently disabled here for an unrelated Vulkan
   particle crash.

7. **`Run` has two overloads distinguished only by delegate shape.** Use named arguments —
   `game.Run(start: Start, update: Update)`.

8. **`GetSimulation()` is core `Stride.BepuPhysics`, global namespace.** Restated because it is the
   single most common misattribution in this codebase.

### Asides — noted, not fixed

- `Program.cs:222` calls `rootScene.GetCamera()` *before* `game.Add3DCamera()` at line 236, so
  `camera` and `simulation` are both null. The `Update` raycast block and the `SoundManager`
  listener never see a camera.
- `using Stride.CommunityToolkit.Helpers` (`Program.cs:27`) is unused, as is
  `using Stride.CommunityToolkit.Engine` in `Client/View/PlayerViewScript.cs` and
  `Client/View/PlayerCamera.cs`.
